# 利用者の声を LP・ストアに載せる（集め方・許可の取り方・載せる形・守ること）

> 2026-10-22 作成（コンテンツ責任者）。関係する正：`company/brand-guardrails.md`（1 実数・3 氏名と引用の明示許諾・5 テンプレは下書き）、`docs/growth-research-2026-10.md` §5・§6（紹介・ステマ規制）、`testflight-recruit.md` §4・§5（テスターの声の許可）、`review-request.md`（レビュー）。
> **LP の「使っている人の声」の枠はもう作ってあり、声が空のあいだは節ごと出ない**（`src/pages/Landing.jsx` の `TESTIMONIALS`・下の §6）。**本物の声が 3 つそろうまで出さない**（`company/marketing-strategy-2026-11.md` §4 の「3 つ集める」）。
> 一言で：**対価なし・実際の利用者・本人の文字での許可・言葉を盛らない**。この 4 つのどれかが欠けたら載せない。

## 1. どこで声を拾うか

| 場所 | 拾い方 | 許可の取り方 | 注意 |
|---|---|---|---|
| **TestFlight の感想（フォーム）** | `testflight-recruit.md` §4 の問い 2・5 の答え。最後の「名前を出さずに引用してよいか」が「はい」の人だけ | フォームの「はい」は**仮の許可**。載せる文面を見せて、§3 の 1 往復で改めて確かめる | 公開前の版の感想なので、公開の版で変わったところに触れる声は載せない（例「◯◯が無い」→ いまは有る） |
| **App Store のレビュー** | App Store Connect の「評価とレビュー」。具体的な場面が書いてある文 | **レビューの文は、本人を特定して許可を取れない**（Apple は書いた人の連絡先を渡さない）。だから **LP・SNS に転載しない**。レビューは App Store のページで読んでもらう | 返信で「LP に載せてよいですか」と聞かない（返信は公開され、ほかの人にも「載せてほしい」と見える） |
| **X・Threads・Instagram** | Orime について本人が自分から書いた投稿（写真で共有の 1 枚・感想・#◯月読了本）。エゴサーチは「Orime」「オリメ 読書」「#◯月読了本 Orime」 | DM で §3 の文。**引用リポストは本人の了解の前にしない**（`sns-playbook.md` §7-4 の 12） | オファーコードを渡した相手（協業・PR）の投稿は、了解があっても **LP・ストア・固定ポストに載せない**（広告の転載＝措置命令の例） |
| **LINE の創業メンバーの部屋** | 部屋の中で書かれた感想 | 部屋の外に出すので、**本人に個別に** §3 の文（部屋のルール 3「本人の許可なく外に出さない」は運営にも適用） | 特典を受けている人の声なので、載せるときは「創業メンバー（開発者への窓口・投票の特典あり）」と添える（§4） |
| **アプリの「フィードバック・要望を送る」** | `feedback` テーブル（設定 → フィードバック・要望を送る）。名前・メールは任意の欄 | メールが書いてある人にだけ §3 のメール。**メールの無い人には取りようがないので載せない** | フィードバックは「不具合・要望を送る場所」として書かれているので、宣伝に使う前提で読まれていない。頼むときはそのことを先に書く |
| **メールの返信**（公開のメール・テスターのメールへの返事） | 返事に書いてあった感想 | そのやりとりの中で §3 の文 | 公開のメールは「1 通だけ」の約束。許可のお願いは**相手が返信してくれたときの返事の中**でだけ（こちらから新しく送らない） |

**拾わないもの**：家族・友人に「書いて」と頼んだ声／自分（運営）の感想／お試しモードの画面に出るサンプルの文／AI が作った答えの文を「声」として載せること。

## 2. どんな声を選ぶか（載せる価値の順）

1. **具体的な場面がある**：「1on1 の前に、部下に任せる話を相談した」「ゼミの発表の前に、本の主張を自分の言葉にした」。場面が無い「便利です」「すごい」は載せない（読む人の役に立たない）。
2. **Orime の 5 つの柱のどれかと一致する**（本と会話する／成果につなげる／習慣にする／発信して続ける／客観的に見る）。LP の節の順に 1 つずつあると強い。
3. **言い過ぎていない**（§5）。
4. **続けて使っている人**（1 週間以上）。はじめての日の興奮だけの声は、数週間後に本人が後悔することがある。

## 3. 許可の取り方（1 往復で終わる形）

> 決まり：**こちらから送るのは 1 通**。返事が無ければ載せない（催促しない）。文面は**載せる形そのもの**（引用する文・名前の書き方・載せる場所）を先に見せて、「これでよいか」だけを聞く。相手に文を書き足してもらわない（事業者が内容に関与しない）。

### 3-1. DM（X・Threads・Instagram・LINE）

```
◯◯さん、こんにちは。Orime を作っている阿部です。
【相手固有の一文：例「『◯◯』を読み終えたあとの 1 枚、拝見しました」】

Orime について書いてくださった言葉を、Orime の紹介ページ（と App Store の説明文）に「使っている人の声」として載せさせていただけないでしょうか。

載せる形は、このとおりです：
―――
「【引用する文・そのまま】」
【名前の書き方：例「30代・営業」】／【使い方の一言：例「1on1 の前に相談している」】
―――

・お名前やアカウント名は出しません（出してよい場合だけ、その旨お知らせください）
・言葉はそのまま載せます。直してほしいところがあれば、おっしゃってください
・載せる場所は、紹介ページ（orime.vercel.app/lp）と App Store の説明文だけです
・お礼や特典はありません（宣伝の決まりで、対価のある声は載せられないためです）
・やめたくなったら、いつでも外します

「これでよいです」の一言だけいただければ十分です。お返事が無くても、載せません。
```

### 3-2. メール（フィードバック・TestFlight の感想・メールの返事）

件名：`Orime の紹介ページに、感想を載せさせていただけますか`

```
◯◯さん

Orime を作っている阿部文哉です。
【相手固有の一文：例「10月の TestFlight の感想で『◯◯』と書いてくださった件です」「先日のフィードバックで教えていただいた◯◯は、直しました」】

その中の次の言葉を、Orime の紹介ページ（と App Store の説明文）に「使っている人の声」として載せさせていただけないでしょうか。

―――

【名前の書き方：例「20代・大学生」】／【使い方の一言】
―――

・お名前・メールアドレスは出しません（出してよい場合だけ、お知らせください）
・言葉はそのまま載せます。直してほしいところがあれば、そのとおりにします
・載せる場所は、紹介ページ（https://orime.vercel.app/lp）と App Store の説明文だけです
・お礼や特典はありません（景品表示法の決まりで、対価のある声は載せられません）
・載せたあとでも、やめたいときはこのメールに返信いただければ外します

「これでよいです」の一言だけで大丈夫です。お返事が無ければ、載せません。

――――――――――――――――

orime.support@gmail.com
```

### 3-3. 許可の記録

返事（「これでよいです」）のスクリーンショットかメールを、**公開物に載せる間ずっと**手元に残す（`brand-guardrails.md` 3「本人の明示許諾メッセージが手元にない限り載せない」）。記録は `company/launch-2026-11/voices/`（git 管理外・個人情報）に、`YYYY-MM-DD_<仮名>.png` のように。載せた声の一覧は下の §7 の表に（名前は書かない）。

## 4. 載せる形

| 項目 | 書き方 | 例 |
|---|---|---|
| 引用 | 本人の言葉**そのまま**。「 」で包む。長ければ**前後を省く**（途中を省くときは「…」）。1 つ 40〜90 字が LP で読みやすい | 「読み終えた本に『任せるのが苦手』と相談したら、自分が線を引いた一行が根拠に出てきて、明日やることが一つ決まった」 |
| 名前 | **既定は匿名**：年代＋立場（「30代・営業」「20代・大学生」「40代・マネージャー」）。本名・アカウント名は、本人が**文字で「出してよい」と言ったときだけ** | 30代・営業 |
| 肩書き・会社名 | **会社名は出さない**（本人が出したいと言っても、会社の許可の問題があるので出さない）。立場は本人の言葉で | ×「◯◯株式会社 課長」 ○「40代・はじめて部下を持った」 |
| 使い方の一言（`how`） | 本人の言葉から。無ければ空 | 1on1 の前に相談している |
| 注記 | 声の節の下に小さく **「実際に使っている方の言葉です（本人の許可を得て、名前は伏せて載せています）」**。創業メンバーの声には「創業メンバー（開発者への窓口・投票の特典あり）」。TestFlight の声には「公開前の版を試した方」 | |
| **変えてよいこと** | 誤字・脱字の直し／句読点／長さの省略（「…」）／「Orime」の表記の統一／本人が「直して」と言った箇所 | |
| **変えてはいけないこと** | 意味・強さ・順番／弱い言葉を強くする（「少し役立った」→「役立った」）／否定を消す（「最初は迷ったけど」を省いて「使いやすい」だけにする）／本人が言っていない機能名を足す／複数の人の言葉を 1 つにつなぐ | |
| 画像・写真 | 本人の写真で共有の 1 枚を載せるときは、**その画像ごと**の許可を別に取る（画像にはロゴと本の表紙が入る。表紙が出版社の画像のときは載せない＝`sns-playbook.md` §7-2 の 4） | |

## 5. 景品表示法とステマ規制で気をつけること

| 気をつけること | なぜ | どうする |
|---|---|---|
| **対価なし** | 対価・特典のある声は「事業者の表示」。LP に載せるなら「PR」が要り、声としての意味が無くなる | お礼・トークン・無料期間・コード・抽選を付けない。協業（オファーコードを渡した人）の声は載せない |
| **実際の利用者** | 使っていない人の声は不当表示 | 1 週間以上使った人・具体的な場面がある声だけ。家族・知人に頼まない |
| **言い過ぎの表現を直さない＝直して載せるのではなく、載せない** | 声に「絶対」「必ず変わる」「忘れなくなった」「読書量が 3 倍に」のような言い切り・数字があるとき、**載せた時点で Orime の表示**になる（優良誤認は事業者の責任）。かといって本人の言葉を弱く書き直せば、本人の言葉ではなくなる | その文は載せない。前後の、場面を語っている部分だけを省略つきで載せるか、その人の声は見送る。本人に「ここをこう直してよいか」と頼まない（内容への関与） |
| **転載しない** | 公開されている投稿・レビューでも、許可なく LP に載せた転載が措置命令の材料になった（大正製薬・ロート製薬） | §3 の許可のあるものだけ。App Store のレビューは載せない |
| **内容を指定しない** | 「こう書いて」「この機能に触れて」は関与 | 見せるのは「載せる形」だけ。書き足し・言い換えを頼まない |
| **関係を隠さない** | 特典を受けている人（創業メンバー）・公開前のテスターの声は、関係を書いておくほうが誠実 | §4 の注記 |
| **数字** | 「◯人が満足」「満足度◯%」は数えていなければ書かない | 声の数は実数（「3 人の声」）。平均の星や件数の自慢は書かない |
| **やめたい人** | 載せたあとでも本人の気持ちは変わる | 「いつでも外す」を約束し、言われたら当日中に外す（LP は再デプロイ・ストアは次の更新で） |
| **個人情報** | 声の記録（返事・連絡先）は個人情報 | `voices/` は git 管理外。載せるのをやめたら記録も消す |

## 6. LP の「声」の枠に入れる手順

LP には**声の枠がもう作ってある**（2026-10 時点）。場所と中身：

| 何 | ファイル | 場所 |
|---|---|---|
| 声のデータ | `src/pages/Landing.jsx` | **106 行目あたり** `const TESTIMONIALS = [];`（空のあいだは節ごと出ない） |
| 表示する節 | `src/pages/Landing.jsx` | **833〜846 行目あたり**「利用者の声（実在の声があるときだけ）」＝`{TESTIMONIALS.length > 0 && (<section … aria-labelledby="lp-voices"> … 見出し「使っている人の声」 … )}` |
| 見た目 | `src/pages/landing.css` | **722〜725 行目あたり** `.lp-voice`（`blockquote`・`figcaption`） |

手順：
1. §3 の許可を取り、`voices/` に記録を残す。
2. `Landing.jsx` の `TESTIMONIALS` に、ファイルのコメントにある形で足す（1 つの声＝1 つの `{ quote, who, how }`。`how` は無ければ省く）：
   ```js
   const TESTIMONIALS = [
     { quote: '【本人の言葉そのまま】', who: '30代・営業', how: '1on1 の前に相談している' },
     { quote: '【本人の言葉そのまま】', who: '20代・大学生' },
   ];
   ```
   表示は `{t.quote}` と `{t.who}／{t.how}` の形（`figcaption` に「／」でつなぐ）。
3. §4 の注記（「実際に使っている方の言葉です（本人の許可を得て、名前は伏せて載せています）」）を、節の中に 1 行足す。**いまの節には注記の行が無い**ので、`</h2>` の次に `<p className="lp-sub">` 等で足す（文字はトークン・`DESIGN.md`）。創業メンバー・テスターの声は `who` の中に書く（例「30代・営業・創業メンバー」）。
4. `npm run demo` → `npm run ui:shots -- after lp` で明暗のスクショを撮り、`ui-critic` で 16 点以上を確かめる（CLAUDE.md の UI のルール 3）。
5. `SPEC.md` の LP の節に「使っている人の声（本物が 3 つそろってから・`TESTIMONIALS`）」と 1 行（UI のルール 4）。
6. デプロイ（`git push origin main`）。外すときは配列から消して再デプロイ。
7. **3 つ未満のあいだは出さない**（1 つだけだと、かえって「集まっていない」と見える）。

App Store に載せるとき（`company/app-store-listing.md` の説明文・プロモーションテキスト）：
- 載せるのは同じ許可の範囲（§3 の文に「App Store の説明文」と書いてある）。許可の文に書いていない場所（スクショの中・動画・広告）には載せない。許可を取り直すときは 1 通から。
- 形は LP と同じ（「 」＋年代・立場＋注記）。スクショの画像の中には入れない（画像の文字は見直しに時間がかかり、外しにくい）。
- 更新は次の審査のとき。載せるのをやめたい人が出たら、次の更新を待たずに**プロモーションテキストだけ**なら審査なしで直せる（説明文は審査が要る）。
