# App Store のレビューを最初の 20 件集める（お願いの文・アプリの中の仕組み・返信の型）

> 2026-10-22 作成（コンテンツ責任者）。公開日 **2026-11-17（火）**。関係する正：`company/marketing-strategy-2026-11.md` §6-5（レビュー依頼は「相談で行動を決めた直後」・Apple の仕組みだけ・見返りなし）、`company/brand-guardrails.md`、`docs/growth-research-2026-10.md` §6（ステマ規制）、`src/lib/reviewRequest.js`（アプリの中の仕組み）。
> **ここで決める線**：レビューを「頼む」のは、①見返りを付けない ②星の数や文の中身を指定しない ③辛口も歓迎する、の 3 つを守る形だけ。`sns-playbook.md` §6・§7-4 と `testflight-recruit.md` 冒頭には「レビュー・星を頼まない」と書いてある。これは「見返りつき・星の指定つきで頼まない」の意味に読み直し、**この文書の形のお願いだけを例外として認めるかは、オーナーが決める**（決めたら `sns-playbook.md` §7-4 の 11 に「見返りなし・星を指定しないお願いは可（`review-request.md`）」と 1 行足す）。決めるまでは (a)〜(c) を出さない。
> なぜ 20 件か：App Store の日本のページは、評価の数が少ないうちは星の平均が出ないか、出ても信頼されにくい。**最初の 20 件は「数」より「本当に使った人の、具体的な文」**が目的（星の平均は追わない・数字の目標を SNS に書かない）。

## 0. 全部に共通の決まり

| 決まり | 理由 |
|---|---|
| **「星 5 を」「高評価を」と頼まない**。頼むのは「使ってみた率直な感想」だけ。良くなかったことも書いてよいと先に言う | App Store の審査ガイドラインは、評価の操作と、評価・レビューの見返りを禁じている（`docs/growth-research-2026-10.md` §6 の 3.2.2・5.6 系）。それ以前に、星を指定したレビューは読む人に見抜かれる＝信頼を減らす |
| **見返りを付けない**（トークン・無料期間・コード・抽選・部屋への招待・「書いてくれた人に◯◯」のどれも） | 同上。景品表示法のステマ規制でも、対価のあるレビューは事業者の表示＝「PR」が要る。レビュー欄に PR は書けないので、対価を付けた時点で載せられない |
| **文の中身・書き方の例を渡さない**（「こう書いてください」の見本・コピペ用の文） | 事業者が内容に関与した表示＝ステマ規制の対象（ロート製薬の措置命令は、文言と画像を指示した例） |
| **実際に使った人にだけ頼む**。家族・知人に「使っていないけど書いて」は頼まない | 実際の利用者でないレビューは不当表示 |
| **1 人に 1 回だけ**。返事が無くても 2 回目を送らない | `brand-guardrails.md` 4（接触は 1 通まで）と同じ規律 |
| 創業メンバー（特典＝窓口・投票を受けている人）には、「創業メンバーとして使っています」と**書き添えてもよい**と案内する（強制しない） | 特典を受けている関係を隠さない（`line-openchat.md` §6・growth-research §6「創業メンバーの特典は見返りと見られうる」） |
| レビューの文を LP・SNS に転載しない。載せる声は `user-voices.md` の手順で本人から別に許可を取ったものだけ | `brand-guardrails.md` 3・転載で措置命令の例（大正製薬・ロート製薬） |
| 数を言うときは実数だけ（「レビュー 12 件」）。「たくさんの方が」と丸めない | `brand-guardrails.md` 1 |

レビューの書き方の案内（Apple の仕組みの説明・内容の指示ではない）：App Store の Orime のページ →「評価とレビュー」→「レビューを書く」。iPhone の App Store アプリからだけ書ける（TestFlight の画面からは書けない）。

## (a) TestFlight のテスターへのお願い（公開日の朝・メール／LINE）

## (d) アプリの中のレビュー依頼（仕組みの説明・オーナーが知っておくこと）

`src/lib/reviewRequest.js`（2026-10-08・`company/marketing-strategy-2026-11.md` §6-5）。

| 項目 | 中身 |
|---|---|
| いつ出るか | **相談の答えから「行動に追加」した直後・はじめての 1 回だけ**（`MyBookBrain.jsx` の `onConsultActionAdded` → `shouldAskForReview()` → `markReviewAsked()` → `askForReview()`）。Orime のいちばんの価値（自分のメモが相談相手になり、やることが決まる）を体感した直後だから。初回起動・作業の途中・エラーの直後には出さない |
| iPhone のアプリで出るもの | **Apple の仕組み（`SKStoreReviewController` の `requestReview`）だけ**。星を付ける Apple の小さな画面が出る。アプリ独自の「レビューを書いてください」の画面・トーストは出さない（審査ガイドライン 5.6 系：独自のレビュー依頼の画面を出さない） |
| 出すかどうか・回数 | **Apple が決める**（1 年に 3 回まで。Orime が頼んでも出ないことがある）。Orime 側は 1 回だけ頼み、2 回目は頼まない（端末に `orime-review-asked-v1` で覚える） |
| プラグイン | ネイティブのプラグイン `InAppReview`（`@capacitor-community/in-app-review`）が入っているビルドだけ。**入っていないビルドでは何も出さない**（独自のトーストで App Store に送ることもしない）。入れるのはオーナーの Mac で `npm i @capacitor-community/in-app-review && npx cap sync ios`（Capacitor 8 に対応した版か確かめる）。**公開の前に入っているか確かめる**（入っていなければ、アプリの中からは一切頼まれない＝この文書の (a)〜(c) だけ） |
| Web（ブラウザ・PWA） | `VITE_APP_STORE_URL` に実 URL が入っているときだけ、無視できるトースト「⭐️ Orime は役に立ちそうですか？よければ App Store のレビューで教えてください。」（9 秒で消える・「レビューを書く」で App Store の `?action=write-review` へ）。未設定の間は何も出ない |
| 見返り | **付けない**（トークン・無料期間など。App Store の規約）。レビューを書いたかどうかをアプリは知らないし、知ろうともしない |
| 文言 | アプリの中の文言は「役に立ちそうですか？教えてください」までで、**「星 5 を」「高評価を」とは書かない**。(a)〜(c) のお願いの文も同じ。星の数を指定したお願いは、Apple の決まりに触れるだけでなく、読む人に見抜かれて信頼を減らす（誠実さの問題） |
| お試し・確かめ方 | iOS シミュレータでは Apple の画面は出ないことがある。実機の TestFlight で「相談 → ここで答えと行動を → 行動に追加」の直後に出るか確かめる（出なくても Apple の判断なので不具合とは限らない） |

## (e) レビューへの返信の型 5 つ

> App Store Connect →「評価とレビュー」から開発者として返信できる（返信は公開される・相手に通知される）。**全部に返す**（1 行でも）。返す前に、相手固有の一文（レビューに書いてある場面・本・困りごと）を足す（`brand-guardrails.md` 5）。返信の中で星の変更・再レビューを頼まない。相手の名前・アカウント名を本文に書かない。不具合は返信で「直しました」と言う前に、実際に直した版が公開されてから。

### 1. 良いレビュー
```
ありがとうございます。【レビューに書いてある場面・本に触れる一文：例「読み終えた本に相談して、明日やることが決まった」という使い方は、いちばん作りたかった形です】
一人で作っているので、こうして書いていただけると、次に直すところを決める支えになります。気づいたことがあれば、アプリの 設定 →「フィードバック・要望を送る」からも、いつでも教えてください。（Orime 阿部文哉）
```

### 2. 不具合のレビュー
```
ご不便をおかけして、申し訳ありません。【起きたこと（レビューの言葉で）】は、こちらでも確かめています。
【直した版が出ているとき：「11月◯日の版（◯.◯.◯）で直しました。App Store で更新のうえ、お試しください」／まだのとき：「原因を調べていて、直り次第「新しくなったこと」に書きます」】
再現する画面や、使っている iPhone の種類など、分かることがあれば orime.support@gmail.com か 設定 →「フィードバック・要望を送る」へいただけると助かります。（Orime 阿部文哉）
```

### 3. 要望のレビュー
```
ご要望をありがとうございます。【要望の内容（レビューの言葉で）】は、【作る予定がある：「次に作るものの候補に入れました。作れることになったら「新しくなったこと」に書きます」／作らないと決めている：「いまは〈理由を 1 文：例 連続日数は入れない方針で作っています〉ので、別の形で〈代わりにできること〉を用意しています」／分からない：「どんな場面で使いたいかを、もう少し教えていただけると、形を考えやすくなります」】
（Orime 阿部文哉）
```

### 4. 解約した人・合わなかった人のレビュー
```
お試しいただき、ありがとうございました。【合わなかった点（レビューの言葉で）】は、そのとおりだと思います。
【直せることなら：「〈何を〉を直して、次の版に入れます」／方針なら：「〈何を〉は、いまはこういう理由で、こうしています」の 1 文】
合わなかった理由を書いていただけたことが、いちばんの助けです。メモや本のデータが必要でしたら、アプリの 設定 →「データをダウンロード」から手元に残せます。（Orime 阿部文哉）
```
（守ること：損失の話を先頭に置かない・割引で引き止めない・「もう一度試して」と頼まない＝`brand-guardrails.md` 4）

### 5. 誤解のレビュー（できることを「できない」と書いている・ほかのアプリと勘違い など）
```
書いていただき、ありがとうございます。【誤解の中身】について、分かりにくくてすみません。
【事実を 1〜2 文・責めない：例「ブクログの記録は、設定 →「ほかのアプリから取り込む」で、書き出したファイルを選ぶと取り込めます」「AI の答えは、入れたメモを材料にしています。メモに無いことは「まだ情報がありません」と返します」】
同じところで迷う方がいると思うので、画面の案内を直します。（Orime 阿部文哉）
```
（「誤解です」「ご理解ください」とは書かない。迷わせた側の責任として、案内を直す）

## 6. 毎週の見方（月曜の朝・5 分）

- App Store Connect の「評価とレビュー」を開き、新しいレビューに全部返す（上の型・固有の一文つき）。
- 実数だけ記録：レビュー【件】・評価【件】・不具合のレビュー【件】・そのうち直した【件】。SNS で言うのは「直した数」だけ（星の平均・件数の自慢はしない）。
- 2 件以上が同じ不具合・同じ誤解なら、`x-posts.md` D07・D14 の【 】に「レビューで多かった声」として入れ、アプリの案内を直す。
- 20 件に届かなくても、(a)〜(c) を繰り返さない（1 人 1 回・1 場 1 回）。あとはアプリの中の Apple の仕組みと、使った人が自分で書くのに任せる。
